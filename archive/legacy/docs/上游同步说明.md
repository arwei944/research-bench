# 上游同步工具使用说明

> 实时跟踪上游(pi-mono / pi-web)最新版本,把新版本同步进 Atlas 的同时,守护「100% 替换率 + 可构建」。

## 核心机制:品牌化重放(brandified replay)

Atlas 两个仓库都是**单提交独立历史**(与上游无 merge-base),因此 `git diff + git apply` 的增量补丁方式**不可靠**(曾实测出现虚假成功、rename 冲突、整体回滚)。

正确同步方式是**品牌化重放**:

```
brandify(upstream/main 全树)   ← 上游最新代码 + 完整 Atlas 化(pi→atlas、.pi→.atlas、@earendil-works/pi-*→@atlas/* 等)
        │  逐文件与本地 HEAD 对比
        ├─ 相等        → 已同步,无需动作
        ├─ 不同(非定制) → 用 brandify(upstream) 覆盖(吸收上游改动 + 保留品牌)
        └─ 不同(定制)   → 保留本地(package.json/lock 的本地内核 file: 引用、人工精简的 README)
```

> **定制文件白名单**(不会被覆盖):`package.json`、`package-lock.json`、`README.md`、`README.ja.md`、`README.ru.md`、`README.zh-CN.md`。这些包含非品牌化的功能性定制,上游改动需要人工合并。

## 工具位置

| 组件 | 路径 | 说明 |
|---|---|---|
| 同步脚本 | `scripts/sync-upstream.sh` | 入口:拉取→状态检测→(按仓库)应用→守护 |
| 品牌化重放 | `scripts/sync-verify-brandify.py` | atlas-web 的验证(默认)与 `--apply`(覆盖非定制文件) |
| 审计工具 | `scripts/replace-audit.py` | 替换率守护(要求 100%) |
| 监控工作流 | `atlas/.github/workflows/sync-upstream.yml` | GitHub Actions 每 6h 检查上游,发现新版本自动开 Issue |

## 快速使用

```bash
# ① 只检查状态(默认)
bash scripts/sync-upstream.sh atlas --check
bash scripts/sync-upstream.sh atlas-web --check

# ② 应用更新
bash scripts/sync-upstream.sh atlas --apply
bash scripts/sync-upstream.sh atlas-web --apply
```

实测输出(2026-09-10, v0.10.5 同步后):
```
$ bash scripts/sync-upstream.sh atlas-web --check
[info] 上游 main: b1a72962d385  上游最新 tag: v0.10.5  本地版本: v0.9.0
brandify(upstream) == HEAD : 504 files (no net change)
  DIFF   CUSTOM package-lock.json
  DIFF   CUSTOM package.json
[ok] 已对齐。残留差异均为 CUSTOM 定制文件,符合预期。
```
> 注意:即使上游 tag(v0.10.5)比本地 `package.json` 版本(v0.9.0)新,只要品牌化重放验证显示非定制文件已对齐,就判定**已同步**——因为 fork 基线本就接近 v0.10.5,功能已全量包含。

## 工具做什么(`--apply`)

**atlas-web(品牌化重放)**:
1. 配置并拉取 upstream
2. 跑 `sync-verify-brandify.py` 验证:非定制文件是否已对齐
3. 未对齐 → `--apply`:用 `brandify(upstream/main)` 覆盖非定制文件(自动吸收上游功能改动 + 保留品牌化),定制文件保留并列出
4. 守护:`replace-audit.py`(替换率必须 100%)+ `npm run build`

**atlas(引擎,仍用版本比对 + git apply)**:
1. 版本比对(本地 `package.json` version vs 上游最新 tag)
2. 生成 `基线tag..upstream/main` 增量补丁 → `git apply --3way` 逐文件应用(冲突收敛)
3. 冲突报告;守护同上

> ⚠️ atlas 引擎的 git apply 方式在单提交历史下**可能同样不可靠**。后续可参考 atlas-web 把 `sync-verify-brandify.py` 推广到 atlas 仓库(品牌化规则在 `rename-to-atlas.py` 中)。当前建议:atlas 同步后务必人工 review + 跑构建验证。

## 「实时」的三种触发方式

| 方式 | 说明 | 配置 |
|---|---|---|
| **手动** | 想起来了跑一次 | `bash scripts/sync-upstream.sh atlas-web --check` |
| **GitHub Actions**(已配) | 每 6h 自动检查上游,新版本自动开 Issue 提醒 | `atlas/.github/workflows/sync-upstream.yml`(以 pi-mono 为主) |
| **本机定时任务** | 每 6h 自动检查 | 见下方示例 |

### 本机定时任务示例

**Linux / macOS(cron)**:
```cron
# 每 6 小时检查一次,有更新时提示
0 */6 * * * cd /c/work/newmax/研究智能体 && bash scripts/sync-upstream.sh atlas-web --check >> /tmp/atlas-sync.log 2>&1
```

**Windows(计划任务)**:任务计划程序 → 新建任务 → 触发器「每天,重复间隔 6 小时」→ 操作运行:
```
bash -lc "cd /c/work/newmax/研究智能体 && bash scripts/sync-upstream.sh atlas-web --check > /tmp/atlas-sync.log 2>&1"
```

## 冲突/差异处理指引

**atlas-web**(品牌化重放):
- 验证输出里标 `SYNC` 的差异 → 直接 `--apply` 自动解决
- 标 `CUSTOM` 的差异(package.json/lock/README)→ 人工合并上游改动:
  - `package.json`:上游新增依赖时,手动合并进依赖表(保留 `@atlas/*` 的 `file:` 引用),再 `npm install` 重新生成 lock
  - README:按需保留人工精简版
- 全部处理完跑:
  ```bash
  PYTHONIOENCODING=utf-8 python scripts/sync-verify-brandify.py   # 应只剩 CUSTOM
  cd atlas-web && npm run build
  ```

**atlas**(git apply):
- 冲突文件手动合并(上游新功能 vs Atlas 化)
- 新增上游文件若含 `pi` 标识,用 `replace-audit.py` 清理
- 构建验证:`cd atlas && npm run build`

> 提示:上游新增代码里的 `pi` 标识会破坏替换率,`--apply` 会自动提示你清理,这是设计好的守护。

## 常见问题

- **为什么 lock 不随上游覆盖?** 我们的 lock 基于本地内核 `file:` 引用生成,与上游 npm 版本树不同;上游新增依赖时重新 `npm install` 即可。
- **会不会覆盖我的定制?** 不会。非定制文件本就是「上游内容 + 品牌化」,覆盖=吸收上游;定制文件(package.json/lock/README)在白名单中保留。
- **atlas-web 有 workflow 吗?** 目前监控以内核(pi-mono)为主;需要时把 `sync-upstream.yml` 复制到 `atlas-web/.github/workflows/`(改上游 URL `agegr/pi-web.git` 与版本文件路径 `package.json`)。
- **如何判定"已同步"?** atlas-web 看品牌化重放验证(非定制文件全对齐);atlas 看版本号相等。
