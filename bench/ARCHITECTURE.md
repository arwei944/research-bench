# 工作台架构重设计

> 日期：2026-10-26 ｜ 状态：待评审
> 结论先行：**现在的架构是「功能容器」，应该改成「研究流水线」。**

---

## 一、诊断：现在有什么问题

先说事实，再下判断。

### 现状盘点

| 维度 | 数字 |
|---|---|
| 应用数 | 7 个 |
| 后端代码 | 5,164 行 (.mjs) |
| 前端页面 | 2,598 行 (.html) |
| 有真实数据的应用 | **2 个**（labset 516K，research 1K） |
| 零数据的应用 | 4 个（learn / scratchpad / mode / design-system / shell） |
| 真实实验次数 | **1 次**（96 次调用） |

### 问题 1：7 个应用里只有 1 个在产出

`labset`（实验器）是唯一有实质数据产出的应用。其余：

- `shell` / `mode` / `design-system` — **是脚手架的自述页面**，不是工具
- `scratchpad` — 空的 demo
- `learn` — 功能完整但**没有任何复习记录**
- `research` — 能跑，但**没做过一次真实研究**

这说明：**我在造「关于工具的界面」，而不是造工具。**

### 问题 2：分层是「装饰性」的，没有约束力

现在有 4 层（平台/基础/应用/实验）、依赖图、影响链。但：

- 依赖图里 7 条边，**没有一条是被平台强制执行的**
- `depViolations` 只在 UI 上标红字，**不影响加载**
- 分层解决的是「认知坐标」，但没解决「运行时约束」

真实的分层应该回答：**L1 挂了，L2 必须降级还是可以继续？** 现在无法回答，因为没有降级契约。

### 问题 3：三套数据模型，互不相通

| 应用 | 数据在哪 | 格式 | 能不能被别处引用 |
|---|---|---|---|
| labset | `data/runs/*.jsonl` | 行记录 | 只有 labset 能读 |
| research | `data/reports/*.md` | Markdown | 只有 research 能读 |
| learn | `data/progress/srs.json` | 键值 | 只有 learn 能读 |

**没有统一的知识/证据层。** 研究产出的结论，无法成为实验器的任务；实验的结论，无法沉淀成可复习的知识卡。

### 问题 4：判分器没有可信度保障机制

这是最严重的一条，而且是刚刚才暴露的：

第一版实验得出「自检有害（-12.5pp）」。真相是——**模型 12/12 全对，验证器把 2 次正确答案误判成错误**。原因是验证器取输出里第一个 A-D 字母，而模型总会先复述选项 (A)、(B)…

修正后结论完全反转：所有配置 pass@1 都是 100%。

**如果没有肉眼核对失败样本，这个错误结论会被当成"发现"记录下来。**

现在加了 `fixtures.mjs`（22 条带标注的历史样本回归），但它是**补丁**，不是机制。架构里必须有位置安放「判分器可信度」。

### 问题 5：前端是 7 份独立 HTML，各写一遍样式

每个应用一个 `index.html`，各自 300–800 行，各自实现主题同步、Markdown 渲染、API 调用。改动一次设计系统，要改 7 个地方（实际只改了 2 个，其余没改）。

## 二、判断：该改成什么样

### 核心转变

```
现在：功能容器
  用户 → 挑一个应用 → 用它 → 数据留在那个应用里

应该：研究流水线
  问题 → 检索 → 假设 → 实验 → 证据 → 结论 → 知识
         ↑___________________________________|
                    （结论反哺新问题）
```

**关键差别**：现在每个应用是**终点**（用完就结束），应该每个环节是**流水线的一站**（产出成为下一站的输入）。

### 新架构：三层

```
┌─────────────────────────────────────────────────────────┐
│  L2  工作流层（Workflow）                                │
│      不是"应用"，是"一条流水线"                          │
│      检索流 / 实验流 / 学习流 —— 每条有明确的输入输出契约  │
├─────────────────────────────────────────────────────────┤
│  L1  能力层（Capability）                                │
│      可组合的原子能力，无 UI，纯函数                     │
│      检索 / 判分 / 评测 / 追踪 / 存证                    │
├─────────────────────────────────────────────────────────┤
│  L0  内核层（Kernel）                                    │
│      实体模型 + 事件总线 + 存储                           │
│      Artifact / Claim / Run / Evidence —— 统一数据模型    │
└─────────────────────────────────────────────────────────┘
```

### 最关键的改变：统一数据模型

现在是「每个应用有自己的数据」。改成**四种通用实体**：

| 实体 | 定义 | 谁产生 | 谁消费 |
|---|---|---|---|
| **Artifact** | 原始产物：一段文本、一个抓取结果、一次模型输出 | 所有环节 | 所有环节 |
| **Claim** | 一条可核验的断言（含来源、置信度、状态） | 检索 / 实验 | 报告 / 知识卡 |
| **Run** | 一次带配置的执行记录 | 实验器 | 证据包 |
| **Evidence** | 支撑某个 Claim 的证据（指向 Run/Artifact） | 实验器 / 核验器 | 报告 |

**为什么这样改**：

- 研究产出的每个结论 → 是一个 `Claim`，带 `evidence: [Run.id]`
- 实验的每次运行 → 是一个 `Run`，能直接挂到 `Claim` 上
- 学习的每张卡 → 指向一个 `Claim`，复习的是**有证据的断言**而不是凭空的知识点

**这就把三个孤立的应用连成了一条链。**

### 判分器可信度必须有位置

在新架构里，它属于 **L1 能力层**的一个组件：`evaluator`

```
evaluator
├── task       任务定义（prompt + verify）
├── fixtures   带标注的回归样本
├── selfTest   双向自检（答案必须过 / 错答必须拒）
└── gate       闸门：fixtures 未过 → 拒绝出证据
```

**闸门是硬约束**：任何进入 `Evidence` 的记录，必须由通过了 fixtures 的 evaluator 产生。这样「判分器错了」不会污染结论层。

## 三、迁移路径（分三步，每步都可停）

不能一次重写完。分三步，每步都能独立交付。

### 第一步：抽内核（不改 UI）

**目标**：把四种实体和存储做出来，现有应用改成读写它。

| 动作 | 产出 |
|---|---|
| 建 `kernel/entities.mjs` | Artifact / Claim / Run / Evidence 的 schema + CRUD |
| 建 `kernel/store.mjs` | 统一存储：`data/kernel/{artifacts,claims,runs,evidence}/` |
| 改造 labset | Run 写入 kernel，而不是自己的 runs/ |
| 改造 research | 报告里的每条结论写成 Claim |
| **不改任何前端** | 前端照常工作 |

**验收**：跑一次实验后，`data/kernel/runs/` 里有记录，`data/kernel/evidence/` 里有证据链。

**风险**：低。可以随时回退（旧数据不动）。

### 第二步：装闸门 + 合并前端

**目标**：让判分器可信度成为硬约束；把 7 份 HTML 合成 1 份外壳 + 应用片段。

| 动作 | 产出 |
|---|---|
| evaluator 组件 | selfTest + fixtures gate |
| Evidence 写入前校验 | 未过 fixtures 直接拒绝 |
| 前端改造 | 抽公共 shell：主题/模式/Markdown/API 一次实现 |
| 应用只提供「内容片段」 | 不再各写一份完整页面 |

**验收**：故意改坏一个 verify → fixtures 失败 → 拒绝出证据。

**风险**：中。前端改造要动 7 个页面，但可以先做 2 个（labset + research）。

### 第三步：连成流水线

**目标**：让结论能反哺新问题。

| 动作 | 产出 |
|---|---|
| 定义流水线契约 | 检索流 / 实验流 / 学习流的输入输出 |
| 三条流跑通一次 | 检索出 Claim → 设计实验 → 跑 → 结论 → 变成复习卡 |
| 淘汰无用应用 | 删掉 scratchpad，合并 shell/mode/design-system 成「设置」 |

**验收**：从一个真实问题出发，走完整条链，产出可复习的知识卡。

**风险**：高（有可能发现契约设计不对）。但前两步的成果仍然有价值。

## 四、明确不做的事

避免重蹈「加功能」的覆辙：

| 不做 | 理由 |
|---|---|
| ❌ 再加新应用 | 7 个里 4 个零数据，先让现有的跑起来 |
| ❌ 再做 10 款设计 | 设计系统已够用，改架构时更该收敛 |
| ❌ 重写分层 UI | 分层的问题是**没有运行时约束**，不是显示不好看 |
| ❌ 引入数据库 | 文件 + jsonl 够用，单用户场景不需要 |
| ❌ 现在就重写全部前端 | 先改 2 个验证模式，再推广 |

## 五、判断依据（诚实说明）

这套方案的**假设**是什么？

1. **假设你需要的是「积累」而不是「更多功能」** — 证据：7 个应用里 4 个零数据
2. **假设研究→实验→学习应该连成一条链** — 这是我的判断，你可能有别的组织方式
3. **假设判分可信度比功能重要** — 证据：刚才那个误判让结论完全反向

**如果不成立会怎样**：

- 如果 1 不成立（你确实需要更多实验工具），那第一步应该先扩任务集
- 如果 2 不成立（三个领域本来就该分开），那不需要统一数据模型，只需各自做深
- 如果 3 不成立……这种情况我不认为是可能的

---

## 六、最小可验证的第一步

如果只做一件事，做这个：

> **把 labset 的 Run 写入 `data/kernel/runs/`，并让 research 的报告结论能引用它。**

这一件事能验证「统一数据模型」是否可行，成本约 1 小时，失败也不影响现有功能。

做完之后，你会立刻知道：这个方向对不对。
